The Stripe Payment Workflow

Every file, every line, and every hop between the browser, Next.js, and Stripe that turns a click on SUBSCRIBE into a recurring $8/month charge.

1. The one-paragraph version

A reader clicks SUBSCRIBE in the masthead. That is a plain HTML form that POSTs to our own route, /api/checkout. The route asks Stripe to create a Checkout Session — a short-lived, hosted payment page — and then redirects the browser to it. The reader types their card details on Stripe's domain, never ours, so no card number ever touches this server. When they pay, Stripe sends them back to /subscribe/success and, separately, sends a signed server-to-server event to /api/stripe/webhook. The redirect is what the reader sees; the webhook is what we actually trust.

The central idea Two things come back from Stripe, and they are not equally trustworthy. The redirect is driven by the user's browser and can be forged by anyone typing a URL. The webhook is signed with a shared secret and comes straight from Stripe's servers. Anything that grants access must hang off the webhook — never off the success page.

2. The whole flow, as a diagram

  1. The click components/Masthead.tsx renders a real <form method="POST">. No client JavaScript is involved, so checkout works even if the JS bundle fails to load.
  2. Session creation app/api/checkout/route.ts calls Stripe with our secret key and describes what is being sold: $8.00 USD, recurring monthly.
  3. Stripe answers with a Session object whose url is a one-time hosted payment page.
  4. The redirect We answer the browser with 303 See Other pointing at that URL. 303 specifically — it tells the browser to switch the POST into a GET when following the redirect.
  5. Payment happens entirely on checkout.stripe.com. Card numbers, 3-D Secure, wallet buttons, and retries are all Stripe's problem, not ours.
  6. The webhook Stripe POSTs a signed checkout.session.completed event to app/api/stripe/webhook/route.ts. This is the authoritative "the money moved" signal.
  7. The return trip Stripe sends the reader to our success_url, substituting the real session id into the {CHECKOUT_SESSION_ID} placeholder.
  8. The receipt page app/subscribe/success/page.tsx looks the session up purely to show a friendly message. If the lookup fails, the reader sees a neutral page — never a stack trace.

4.4 — The webhook: the part you actually trust

12const MAX_BODY_BYTES = 1_048_576; 1 MB ceiling. Real Stripe events are a few KB. This bounds the buffering done by request.text() — which happens before signature verification and is therefore reachable by anyone on the internet, not just Stripe.
21 const secret = process.env.STRIPE_WEBHOOK_SECRET; A different secret from the API key (whsec_…). It is the shared key used to sign the payload.
22 const signature = request.headers.get('stripe-signature'); Stripe's header carrying a timestamp and one or more HMAC-SHA256 digests of the raw body.
24 const contentLength = Number(…'content-length'); Checked before the read. The guard cannot move later: by the time the body has been read, the unbounded buffering it exists to prevent has already happened.
26 return json({ error: 'payload too large' }, 413); 413 Content Too Large.
32 const rawBody = await request.text(); Raw text, never request.json(). The signature is a hash of these exact bytes; a round trip through JSON.parse and back would reorder keys and change whitespace, and verification would fail forever. This is the single most common way a Stripe webhook gets broken.
36 if (!secret || !signature) return … 400; A missing secret is a misconfiguration, and the safe reading of a misconfigured verifier is "reject" — never "accept unverified". Note it returns the same generic 400 as a bad signature, so probing tells an attacker nothing.

It recomputes the HMAC, compares in constant time, and rejects timestamps outside a tolerance window — which is what stops an attacker replaying a captured "payment succeeded" event. It throws on failure; it returns a typed Stripe.Event on success.
44 if (error instanceof MissingStripeKeyError) … 503 Again separating "not configured" from "not authentic".

51 const session = event.data.object; The Checkout Session as Stripe saw it at completion — narrowed to the right type by the event.type check above.
52 console.info(`[stripe] checkout.session.completed …`); Today the handler only logs id, payment_status and email. That is the honest current state: nothing is gated behind the subscription yet, so there is nothing to unlock.
58 return json({ received: true }); 200 quickly, for every verified event including ones we ignore. A non-2xx makes Stripe retry with backoff for days; slow work belongs in a queue, not in this response.
Not yet handled — and deliberately so The route acknowledges every verified event but only acts on checkout.session.completed. A production subscription business also needs invoice.paid (the renewal each month), invoice.payment_failed (dunning), and customer.subscription.deleted (cancellation). It also needs idempotency: Stripe can deliver the same event more than once, so any state change must be keyed on event.id.

6. Testing it locally

Webhooks in development. Stripe cannot reach localhost, so forward events with the Stripe CLI. It prints the whsec_… to put in .env.local:

stripe listen --forward-to localhost:3000/api/stripe/webhook
stripe trigger checkout.session.completed

Test cards. 4242 4242 4242 4242 succeeds; 4000 0000 0000 9995 is declined for insufficient funds. Any future expiry and any CVC.

The repo's own check. scripts/verify-stripe.sh runs two phases: Phase A proves the site is unharmed by an unconfigured payment integration and needs no Stripe account at all; Phase B creates a real Checkout Session, and runs only when STRIPE_SECRET_KEY is exported into its environment.

7. Why it is built this way

DecisionReasoning
Hosted Checkout, not a custom card formCard details never reach our servers, which keeps PCI scope with Stripe and gets 3-D Secure, wallets, and localisation for free.
Plain HTML formPayment works without client JavaScript, and there is no fetch/CORS/redirect-handling complexity.
Inline price, not a dashboard Price IDA fresh Stripe account needs only API keys. The cost — no product catalog entry — is acceptable while nothing is gated.
Lazy Stripe clientThe masthead is on every page; a module-scope client would make one missing env var take down the whole site.
Raw body in the webhookSignature verification hashes the exact bytes. Parsing first breaks it permanently.
Success page grants nothingThe URL is user-controlled and forgeable. Only the signed webhook is evidence that money moved.
Distinct 503 / 502 / 400 codesEach tells an operator a different true thing: not configured, upstream failed, not authentic.
